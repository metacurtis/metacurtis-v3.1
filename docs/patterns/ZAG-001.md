# Zero-Assumption Grounding Diagnostic (ZAG-001)

**Pattern ID:** ZAG-001  
**Category:** Diagnostic / AI-Native Methodology  
**Status:** Active  
**Created:** 2025-12-15  

---

## Overview

Diagnostic methodology that treats training-data knowledge as a liability. It forces evidence-gathering from the actual codebase before proposing fixes, especially when the AI feels confident.

### Also Known As
- Phenomenological Grounding Diagnostic
- First-Principles Reality Map
- Confidence-Inversion Diagnostic

---

## Core Problem

High LLM confidence usually means strong training-data pattern match, which often diverges from this repo. Result: plausible-but-wrong fixes and hours of chasing false paths.

```
High confidence → Pattern from training data → Not this repo → Wrong fix
```

---

## Principle

> **Treat every assumption as suspect until grounded in observed repo reality.**

Standard vs ZAG:

| Standard LLM | Zero-Assumption |
| --- | --- |
| Assume architecture → debug | Map architecture → find cause |
| “This pattern usually works” | “What does THIS code do?” |
| Confidence = correct | Confidence = bias risk |
| Training data as knowledge | Training data as bias |
| Propose → implement → debug | Observe → understand → implement once |

---

## When To Apply

- Standard debugging failed
- AI expresses high confidence / “common pattern”
- Integration points and race conditions
- “It should work” failures
- Custom architecture divergences

---

## Diagnostic Template (Sections)

1) **Observable State**: DOM/screen, runtime refs/state, console logs (order).  
2) **Component/System Map**: Mounted tree, parent-child, conditionals; imports/deps; ownership of events.  
3) **Event/Execution Trace**: Timestamped events with listener counts; subscription timing; branches/early returns taken.  
4) **Branch Analysis**: All flag/condition checks; implicit dependencies and required sequences.  
5) **Comparative Trace**: Working vs broken, divergence point, differences.  
6) **Requirements Extraction**: Guard conditions for success; actual vs required state; init order required vs actual.  
7) **Break Localization**: Last successful step; first failed step; why it failed; root cause.

---

## Output Format

Structured JSON (no assumptions), e.g.:

```json
{
  "observableState": {...},
  "systemMap": {...},
  "eventTrace": {...},
  "branchAnalysis": {...},
  "comparativeTrace": {...},
  "requirements": {...},
  "breakLocalization": {...}
}
```

---

## Usage Protocol

1. Detect trigger phrases (“should work”, “common pattern”, high confidence).  
2. Halt solutions; run all ZAG sections.  
3. Only after mapping reality, propose fixes tied to evidence.  
4. Document findings and link to patterns/postmortems.

## Integration with v3.7 Orchestration

- Expanded form of Agent F’s diagnostic mode.  
- Use when F:diagnostic isn’t surfacing root cause or when confidence is high.  
- Lane: `F:diagnostic → (ZAG if confident) → A → B → ...`

---

## Anti-Patterns

- Partial grounding then proposing fixes
- Interpreting while collecting (keep observation vs interpretation separate)
- Confirmation bias (looking for evidence to match a suspected cause)
- Skipping comparative trace
- Declaring root cause before completing all sections

---

## Example Application (from demo debugging)

- Screen: loader overlay on top of canvas; HUD visible.  
- Events: first RENDER_DIRECTIVE listenerCount=0 (missed), renderer subscribed later.  
- Divergence: demo beats fired before renderer subscription.  
- Root cause: beats emitted too early; overlay not dismissed.  
- Fix: wait for renderer ready signal before starting demo; dismiss overlay.
